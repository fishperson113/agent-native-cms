# Milestone 8 — Admin and tenant credential management

## Status

Implemented on 2026-08-28.

## Goal

Replace the single environment API key and environment tenant ID with database-backed, fixed, revocable credentials. Support exactly two authorization classes: `admin` and `tenant`.

## Authorization model

| Role | Scope | Intended use |
|---|---|---|
| `admin` | Global control plane | Create/disable tenants, issue/revoke keys, inspect runtime/audit records, and moderate or delete tenant articles |
| `tenant` | Exactly one tenant | Use article and presentation tools only for the tenant bound to the key |

An admin credential is primarily a control-plane credential, not an implicit content tenant. It may inspect and delete articles across tenants for moderation and operations, but it does not create, rewrite, publish, or upload presentations through tenant authoring tools. To author tenant content, use a credential bound to that tenant. This keeps existing tenant content tool schemas free of caller-supplied `tenantId` values.

## Key policy

- A key is generated by the server with cryptographically secure randomness.
- Plaintext is shown exactly once when issued.
- PostgreSQL stores only a keyed lookup prefix and a strong hash, never the plaintext secret.
- A key value is fixed: there is no automatic rotation.
- Rotation means issue a new key, update the agent, then revoke the old key.
- Revocation is immediate for new requests and closes active sessions authenticated by that key.
- Multiple tenant keys may be issued when separate agents need independently revocable access.
- Keys have a human-readable name, creation time, optional note, last-used time, and `revokedAt`.
- Expiry is omitted from the first version unless later required.

## Data model

### `mcp_credentials`

- `id` UUID primary key.
- `role` enum-like text: `admin | tenant`.
- `tenant_id` nullable FK; required for `tenant`, forbidden for `admin`.
- `name` for operator recognition.
- `key_prefix` indexed and non-secret.
- `key_hash` secret verifier.
- `created_at`, `last_used_at`, `revoked_at`.

Database constraints must enforce the role/tenant relationship, not only TypeScript checks.

## Bootstrap and management

### Bootstrap

- Add a one-time terminal command that creates the first admin credential.
- Require an explicit confirmation or environment bootstrap secret.
- Print the plaintext key once and never log it again.

### Terminal-first admin commands

- List tenants.
- Create or disable a tenant.
- Issue an admin or tenant key.
- List credential metadata without key hashes.
- Revoke a credential.
- List active MCP sessions and close a selected session.
- Find and inspect articles by tenant for moderation.
- Delete an article by explicit `tenantId` and `articleId`.

These commands use application use cases, not direct SQL. The same use cases can later be exposed as admin MCP tools or a web dashboard without duplicating policy.

## Migration behavior

- Provide an explicit migration command that imports the existing `CMS_TENANT_ID` and API key as one tenant credential.
- Keep the old environment-key authentication behind a temporary compatibility flag for one milestone only.
- Remove normal runtime dependence on `CMS_TENANT_ID` and `CMS_MCP_API_KEY` at M9 exit.

## Acceptance tests

- A generated tenant key authenticates and resolves exactly one tenant.
- An admin key authenticates without a tenant binding.
- Plaintext keys and hashes never appear in normal logs or list output.
- Revoked keys receive `401` and their active sessions are closed.
- Two keys for one tenant can be revoked independently.
- Disabled tenants cannot create new MCP sessions.
- Key-prefix collisions are handled safely.

## Exit criteria

- The operator can create a tenant, issue its fixed key, and revoke it from the terminal.
- Authentication resolves an immutable actor context from PostgreSQL.
- Credential secrets are hashed and never recoverable from the database.
- Every credential operation is ready to emit an audit event in M10.

## Implemented result

- PostgreSQL stores admin/tenant credential metadata, unique lookup prefixes, scrypt hashes, usage time, and revocation time with a database role/tenant constraint.
- New fixed keys are generated with secure randomness and shown once; the original M7 key can be imported idempotently without changing its plaintext value.
- HTTP authentication resolves tenant scope from the database on every request, rejects disabled tenants, and closes a session when its credential is observed revoked.
- The terminal control plane creates/disables tenants, bootstraps admin, issues/lists/revokes credentials, imports the environment key, and performs explicit tenant-scoped article moderation/deletion.
- Admin MCP tools and direct in-process session controls remain M9 work. A separate terminal process cannot reliably inspect or mutate the running process's in-memory session map.
- The local development database has migrated its existing environment tenant key and disabled legacy fallback in `.env`.

## Non-goals

- User accounts, memberships, invitations, passwords, OAuth, SSO, or fine-grained roles.
- Automatic key rotation.
- Browser UI for key management.
